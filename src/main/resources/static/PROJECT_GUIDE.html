2. How a request moves through the application

Browser page ↓ fetch / XMLHttpRequest Spring Boot REST controller ↓ authentication, role and group checks Service / business rules ↓ repository and Firestore data service Firestore or Firestore emulator ↓ response Browser updates the page

The frontend is not the financial authority. Loan amounts, interest, balances, payment allocation, and access decisions are validated by the backend.

Main areas

  • Authentication and role-based access.
  • Bachat Gat groups and member records.
  • Savings, income, expenses, transactions, loans, and repayments.
  • Administrative dashboards and loan-detail screens.
  • Document upload and protected document access.

3. Safe local setup

Use two PowerShell windows. The emulator window must stay open.

Window 1: start Firestore emulator

gcloud emulators firestore start --host-port=127.0.0.1:8081

Window 2: start the application

cd "C:\Users\hariom\Desktop\bhachat_investment\BachatGat-InvertUR-Money-2c800011b97c8d8c2e1d84fb3827df6777ec825e"

$env:FIRESTORE_EMULATOR_HOST="127.0.0.1:8081"
$env:FIRESTORE_EMULATOR_ENABLED="true"
$env:GCP_PROJECT_ID="bachat-gat-local"
$env:APP_DEMO_DATA_ENABLED="true"
$env:SPRING_PROFILES_ACTIVE="dev"

mvn spring-boot:run "-Dspring-boot.run.profiles=dev"
Local-only settings: the local project name and emulator host keep test data away from the production Firestore project.

Open http://localhost:8080. Stop the application with Ctrl+C in Window 2, and stop the emulator with Ctrl+C in Window 1.

4. Security and data safety

  • Production must not enable demo-data reset or seed behavior.
  • Document access requires authentication and the correct Bachat Gat group.
  • Unknown document IDs return not-found rather than generated fake documents.
  • Uploads require validation and sanitized filenames.
  • Payment webhooks require signature verification.
  • Financial updates use duplicate/idempotency safeguards and backend allocation.
  • Never place secrets in this HTML file, source control, browser code, or screenshots.

Before any production data operation, verify the active project and bucket explicitly. Local emulator data and cloud Firestore data are separate environments.

5. Loan calculation rules

The loan calculator uses reducing-balance interest. Monthly interest is calculated from the actual opening outstanding principal, not always from the original loan amount.

monthly interest = opening outstanding principal × monthly rate
closing principal = opening principal − actual principal paid

The schedule keeps scheduled principal separate from carried pending principal. An interest-only payment or missed payment does not reduce closing principal because no principal was actually paid.

SituationClosing principalPending values
Normal EMIReduces by actual principal paid.Unpaid dues carry forward.
Interest onlyUnchanged.Scheduled principal becomes pending.
No paymentUnchanged.Interest and principal both carry forward.
Partial paymentReduces only by allocated principal.All unpaid amounts remain pending.
Example: A ₹50,000 loan with ₹500 interest-only payment in month 1 correctly remains at ₹50,000 closing principal. It reduces only after a later payment is allocated to principal.

Internal calculations use BigDecimal. The normal interface displays whole rupees using half-up rounding.

6. Testing and verification

Run the full test suite

mvn test -B

Run calculator tests only

mvn -q -Dtest=FinancialCalculatorTest test

Important scenarios include normal repayment, interest-only payment, missed payment, partial payment, final principal adjustment, zero interest, invalid values, duplicate payments, concurrent attempts, and cross-group access.

For a manual restart-persistence test, create a local test record, stop the app, start it again with the same emulator, and verify the record remains. Do not use this procedure against production unless a separate approved test record and backup plan exist.

9. Complete setup on a new Windows machine

This repeatable path installs the tools, downloads the code from GitHub, verifies the checkout, and runs the first build before local runtime troubleshooting.

9.1 Install prerequisites

  1. Install Git for Windows from git-scm.com.
  2. Install a JDK 21 distribution. A JDK includes the compiler Maven needs; a JRE alone is not enough.
  3. Install Apache Maven 3.9 or newer, or use the Maven Wrapper if the repository provides one.
  4. Install the Google Cloud CLI and the Cloud Firestore Emulator component.
  5. Optional: install IntelliJ IDEA or VS Code. An IDE is not required to run the application.

9.2 Verify the tools

git --version
java -version
mvn -version
gcloud version

Expected: Git, Java 21, Maven 3.9+, and a working Google Cloud CLI. If a command is not recognized, repair the Windows PATH before continuing.

9.3 Clone the code from GitHub

New-Item -ItemType Directory -Force "$env:USERPROFILE\source\repos" | Out-Null
cd "$env:USERPROFILE\source\repos"
git clone https://github.com/Harriom1/Bachat_Gat.git BachatGat
cd .\BachatGat
git status
git branch --show-current

Never paste passwords, API keys, JWT secrets, or service-account JSON into GitHub. Verify the clone contains pom.xml, src\main\java, and src\main\resources\static.

9.4 First build

mvn clean test -B

This downloads dependencies, compiles the backend, runs automated tests, and proves that the checkout is complete before runtime troubleshooting begins.

How to stop and restart

  1. Press Ctrl+C in Window 2 to stop Spring Boot.
  2. Press Ctrl+C in Window 1 to stop the emulator.
  3. Start the emulator again first, then run the application again with the same dev variables.
  4. Use the same emulator data directory or export/import procedure if persistence between emulator processes is required by the test plan.

11. Database, emulator, and old-data recovery

Firestore is the application database. FirestoreConfig selects the client configuration, FirestoreDataService provides shared persistence behavior, and repository classes keep data access out of controllers. The local emulator and cloud Firestore are different databases.

gcloud auth list
gcloud config get-value project
gcloud projects describe bachat-gat-development
gcloud firestore databases list --project=bachat-gat-development

These are read-only checks. Run them only when you intentionally want to inspect the cloud project. Never point local demo mode at production Firestore.

Why old records may appear missing: the app may be connected to the emulator, a different GCP project, a different database, or a different group ID. A changed user ID or group assignment can also make records invisible through authorization even when the records still exist.

Safe investigation sequence

  1. Record the environment variables and active Spring profile.
  2. Confirm the project ID and Firestore database without modifying data.
  3. Confirm the authenticated user ID and group ID.
  4. Check application logs for the collection/path being queried.
  5. Only after approval, export or back up the relevant cloud data before any repair.

12. Authentication, authorization, and login troubleshooting

The login flow is: browser form → AuthController → AuthService → user lookup and password-hash verification → JWT creation → JWT filter on later requests. Authentication answers “who are you?” Authorization answers “may this user perform this action?”

SymptomMeaningSafe check
401Missing or invalid login token.Log in again and inspect the active service revision/profile.
403User is known but not allowed to perform the action, or a proxy/security rule denied it.Check role, group membership, route authorization, and Cloud Run logs.
Login rejects an old passwordThe user record may be in another database, the password may have been reset, or the username may not match.Verify the active database and user document through an authorized read-only check.
Local login differs from cloud loginLocal emulator data is separate from production data.Use the intended profile and seed only the local emulator.

This guide intentionally does not contain passwords, password hashes, reset tokens, JWTs, service-account keys, or personal contact details. Store secrets in Secret Manager or an approved local secret mechanism.

15. Backup, restore, and rollback procedure

  1. Record the active project, Firestore database, storage bucket, Cloud Run service, and current revision.
  2. Create an approved backup/export before changing production records or security settings.
  3. Test restoration in a separate project or emulator before touching production.
  4. Deploy a new Cloud Run revision without deleting the previous revision.
  5. Verify health, login, group isolation, documents, loans, and payments.
  6. If the new revision is unhealthy, route traffic back to the last known-good revision and investigate logs.
Never use emulator reset, collection deletion, or recursive bucket deletion as a recovery step. Resolve the exact environment and obtain approval before any destructive action.
